\section{Project Title}

\textbf{DataSim: A General-Purpose Simulation Lab for High-Impact Database Scenarios.}

\textbf{Scenario family:} Shared-resource workflows covering inventory, reservations, payments, banking, collaboration, job processing, and quota management.

\section{Introduction and Background}

Database systems support applications where many users and clients read and modify shared data at the same time. A database may appear correct during a single-user demonstration but behave incorrectly when concurrent requests arrive together. Examples include lost updates, inconsistent reads, race conditions, lock waits, deadlocks, and constraint violations.

\datasim{} is a general-purpose interactive database simulation lab that makes these behaviors visible. Like a focused learning simulator such as Cisco Packet Tracer, it provides approachable interfaces for constructing and observing scenarios without requiring users to manage every low-level detail manually. DataSim supports repeatable scenarios and technical views for examining transactions, locks, constraints, isolation levels, and results across domains that depend on shared state.

The project targets high-impact database situations: preventing inventory overselling, allocating the last seats or rooms fairly, making payment and order requests idempotent, maintaining consistency during bank transfers, merging collaborative edits, assigning jobs without duplication, and enforcing quotas or rate limits. These scenarios share the same underlying problems of concurrent reads, writes, ownership, allocation, and recovery. Future scenarios can reuse the platform's controls, database instrumentation, experiment runner, and result visualizations.

\section{Problem Statement}

The initial implementation demonstrates a shared-resource race in which several clients belonging to one owner may attempt to claim a limited resource at nearly the same time. The same pattern appears when customers buy the last product, travelers reserve the last seat, workers claim the same job, or two services update one account simultaneously. Each request can read the same database state before writing. If the operations are not coordinated correctly, the system may oversell inventory, double-allocate a resource, lose an update, charge twice, or violate a quota. DataSim keeps the database techniques domain-independent so the same controls can represent any of these situations.

The project addresses the following problem:

\begin{quote}
How can a relational DBMS maintain a correct, real-time shared state under concurrent operations, and what correctness and performance trade-offs are introduced by different transaction, isolation, locking, and constraint strategies?
\end{quote}

\datasim{} also demonstrates the lost-update problem. The same anomaly can affect stock counts, account balances, document versions, counters, and job status when concurrent read-modify-write operations overwrite one another.

\section{Objectives}

\begin{enumerate}
\item Model shared users, resources, operations, events, and experiment results in a normalized relational database.
\item Demonstrate concurrency anomalies using reproducible scenarios rather than only theoretical examples.
\item Compare naive operations, transactions, serializable isolation, pessimistic locking, optimistic version checks, unique constraints, triggers, and a Redis lease strategy.
\item Show how isolation levels affect visibility, blocking, deadlocks, and correctness.
\item Visualize transaction schedules, lock information, wait-for relationships, rollbacks, and invariant checks.
\item Simulate scalable groups of virtual users using real database transactions across reusable scenario patterns.
\item Provide a friendly interface for learners and a technical interface for detailed inspection.
\item Persist experiment configurations and results so that runs can be compared and analyzed.
\item Keep the platform extensible so future scenarios can reuse the same simulation and measurement patterns.
\end{enumerate}

\section{Scope of the Project}

\subsection{Included}
\begin{itemize}
\item MySQL 8.4 relational database using the InnoDB storage engine.
\item A relational schema for users, resources, allocations, operations, events, and experiment runs.
\item Shared-resource limits, leases, and expiry rules that can represent quotas, reservations, inventory, or work allocation.
\item Multiple concurrency-control strategies for the same business operation.
\item Lost-update experiments using a shared counter and other read-modify-write patterns.
\item Transaction Stepper for statement-by-statement execution of two transactions.
\item Concurrency Lab for repeated race experiments and measurement.
\item Simulation Control Room for virtual users and real database traffic.
\item InnoDB lock and wait-for information where available.
\item Invariant checks for quotas, leases, duplicate allocations, and audit consistency.
\item React web interface, Node.js/TypeScript API, Docker setup, and automated tests.
\end{itemize}

\subsection{Excluded}
\begin{itemize}
\item Real domain services such as inventory fulfillment, payment processing, banking, reservations, collaboration, or content storage; DataSim models database behavior rather than operating these services.
\item Production authentication, authorization, subscriptions, or payment processing.
\item Production-scale cloud deployment or guaranteed multi-region availability.
\item Personalization, recommendations, advertising, and social networking.
\item Any claim that the implementation represents the internal design of a commercial banking, retail, reservation, collaboration, or payment service.
\item Unlimited arbitrary workloads; the simulator uses bounded, controlled scenarios for repeatability.
\end{itemize}

\section{Requirement Analysis}

\subsection{Users}
\begin{longtable}{p{0.25\textwidth}p{0.65\textwidth}}

\textbf{User} & \textbf{Main needs}\\
\midrule
Student or learner & Understand DBMS concepts through guided visual scenarios.\\

Developer & Add new database strategies or scenarios without replacing the platform.\\
\bottomrule

\subsection{Data to be stored}
\begin{itemize}
\item \textbf{User/account:} identity, quota or limit, conflict policy, state version, and laboratory flag.
\item \textbf{Client:} owner, name/type, and last-seen time.
\item \textbf{Resource:} descriptive attributes, availability, capacity, and shared counters.
\item \textbf{Allocation/operation:} user, resource, status, quantity, timestamps, lease, and strategy.
\item \textbf{Operation event:} state transition, references, timestamp, version, request id, and details.
\item \textbf{Experiment run:} type, strategy, configuration, outcomes, latency, throughput, violations, and batch id.
\end{itemize}

\subsection{Required operations}
\begin{enumerate}
\item Look up a user/account and its clients or owned resources.
\item Create, update, reserve, release, or cancel a shared resource operation.
\item Renew a lease or heartbeat for an in-progress operation.
\item Resolve conflicts according to a selected policy.
\item Reject expired, preempted, duplicate, or stale client requests.
\item Switch the active concurrency strategy.
\item Run quota, allocation, and lost-update experiments.
\item Step through two transactions one statement at a time.
\item Start, pause, resume, repair, and stop a crowd simulation.
\item Inspect live state, audit events, locks, and experiment history.
\end{enumerate}

\subsection{Information to retrieve and analyze}

The system retrieves active sessions per account, invariant status, lost updates, transaction outcomes, retries, deadlocks, rollbacks, lock waits, latency percentiles, throughput, violation counts, event timelines, and strategy comparisons.

\subsection{Functional requirements}
\begin{enumerate}
\item The system shall store user, client, resource, allocation, event, and experiment data.
\item The system shall support concurrent claims, updates, allocations, or reservations from multiple users or clients.
\item The system shall implement and compare multiple protection strategies.
\item The system shall record experiment configurations and results.
\item The system shall expose invariant and consistency checks.
\item The system shall provide friendly scenario controls and technical inspection views.
\item The system shall reject expired, preempted, duplicate, or stale operations.
\end{enumerate}

\subsection{Non-functional requirements}

The system must provide correctness, repeatability, observability, bounded scalability, maintainability, local portability, and usability. Experiments must be controlled and their results must be persisted for later comparison.

\section{Database Selection and Justification}

\subsection{Selected technology}
\begin{itemize}
\item \textbf{Database:} MySQL 8.4.
\item \textbf{Type:} Relational database management system.
\item \textbf{Storage engine:} InnoDB.
\item \textbf{Additional component:} Redis 7 for an optional lease-based comparison strategy.
\item \textbf{Application stack:} Node.js, TypeScript, Express, React, and Socket.IO.
\end{itemize}

A relational DBMS is appropriate because \datasim{} studies transactions, isolation levels, row and gap locks, constraints, foreign keys, deadlocks, and consistency of related entities. MySQL/InnoDB provides these mechanisms in a real database engine, allowing the project to measure actual behavior rather than simulate every rule in application code.

MySQL was selected because InnoDB supports ACID transactions and multiple isolation levels; row-level and next-key locking; foreign keys, unique constraints, checks, triggers, and generated columns; performance-schema lock inspection; and reproducible Docker-based execution. Redis is included as a separate comparison point to show how an external key-value lease gate can coordinate access while MySQL remains the durable relational source of truth.

\subsection{Relational schema}

\begin{lstlisting}
USER_ACCOUNT(account_id PK, username UNIQUE, quota, conflict_policy,
        state_version, is_lab)

CLIENT(client_id PK, account_id FK -> USER_ACCOUNT, client_name,
        client_type, last_seen_at, UNIQUE(account_id, client_name))

RESOURCE(resource_id PK, resource_name, resource_type, capacity,
          shared_counter)

ALLOCATION(allocation_id PK, client_id, account_id, resource_id FK -> RESOURCE,
            status, quantity, started_at, lease_expires_at,
            ended_at, strategy,
            FK(client_id, account_id) -> CLIENT(client_id, account_id))

OPERATION_EVENT(event_id PK, account_id, client_id, allocation_id, event_type,
                  state_version, client_request_id, created_at, detail,
                  UNIQUE(client_id, client_request_id))

EXPERIMENT_RUN(run_id PK, experiment, strategy, config, outcomes,
               violations, p50_ms, p95_ms, throughput, batch_id, created_at)
\end{lstlisting}

\subsection{Keys and constraints}
\begin{itemize}
\item Primary keys identify every user, client, resource, allocation, event, and run.
\item Foreign keys preserve ownership and reference integrity.
\item A composite foreign key ensures that an allocation's client belongs to its recorded account.
\item Unique username and account/client-name constraints prevent duplicate identities.
\item A unique client/request-id constraint makes state-changing requests idempotent.
\item Status, policy, quota, quantity, capacity, and counter checks reject invalid values.
\item An optional generated-column unique index demonstrates declarative protection for one active allocation per account.
\item Allocation limits are predicates over multiple rows, so they require concurrency control rather than only a primary key.
\end{itemize}

\textbf{Core invariant pattern:} For every shared owner or resource, active allocations and consumed quantity must remain within the configured quota or capacity.

\subsection{Normalization}

The core schema follows third normal form. Each table represents one main entity or event type; attributes are atomic; non-key attributes depend on the whole key; and client, resource, event, and experiment details are not unnecessarily duplicated. The allocation table intentionally stores both \texttt{client\_id} and \texttt{account\_id} because owner-level queries and locking are central to the workload. The composite foreign key keeps this controlled denormalization consistent.

\subsection{Scenario workflow}

\begin{enumerate}
\item A user selects a scenario and concurrency strategy in the React interface.
\item The interface sends an operation, experiment, or simulation request to the Node.js API.
\item The service begins a MySQL transaction and reads the relevant shared state.
\item The selected strategy applies locking, isolation, optimistic checks, constraints, or an external lease.
\item MySQL returns a grant, rejection, wait, deadlock, rollback, or conflict result.
\item The service commits or rolls back, records an event or experiment result, and publishes committed state.
\item The interface displays updated sessions, metrics, checks, timelines, and technical diagnostics.
\end{enumerate}

\subsection{System output}

The system produces friendly scenario and simulation views, live user/client/resource state, strategy verdicts, transaction schedules, lock and wait information, experiment history, latency and throughput measurements, violation counts, and CSV/Markdown results for analysis.

\section*{Conclusion}

\datasim{} is designed as a general-purpose simulation lab for studying database behavior under concurrency. It addresses high-impact patterns such as overselling, double allocation, duplicate payment requests, inconsistent transfers, lost edits, duplicate job claims, and quota violations. Its domain-neutral entities and diagrams make the project applicable to many systems without exposing one particular business domain at the high level. By connecting friendly interfaces to real MySQL transactions and measurable outcomes, the project shows how database design choices affect correctness, performance, and scalability across different systems.
